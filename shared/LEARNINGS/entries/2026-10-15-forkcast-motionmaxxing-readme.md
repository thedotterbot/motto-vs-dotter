## What it is

No host, no talking head, no speech observed. A fast,
continuous scroll through a dense technical README for an
agent skill for motion graphics. Beats: README top
(project title, tagline, badges, intro) → showcase section
with an embedded demo clip labeled as the before version
plus text about frame checks → a rating-scale table
grading video quality from low to high → a section on what
a good video looks like, followed by a checklist of
generic AI-motion flaws (flat timing, generic movement,
weak typography/layout) → scrolls back to the README top
and loops.

## What works and why (the content, not the funnel)

- **The doc IS the content.** Zero production overhead:
  the work artifact (the README) is the reel. The scroll
  itself is the video. For a technical audience, showing
  the real artifact beats performing enthusiasm about it.
- **Grading scale creates a self-assessment loop.** A
  low-to-high rating table makes the viewer ask "where
  does MY work fall?" That question is a loop — the viewer
  keeps watching to place themselves. Same loop engine
  as Remy's open questions, applied to a scale instead
  of a promise.
- **Specificity for the niche.** Named flaw patterns,
  a grading scale, a diagnostic checklist. Tight,
  developer-focused wording signals "this is for
  practitioners." Audience filtering as a feature: the
  reel does not try to be for everyone.
- **Before/after demo as evidence.** The embedded demo
  clip is the proof — even without metrics, showing a
  before version next to the claim of improvement beats
  claiming it in text alone.
- **One moving element in a still frame.** The animated
  demo inset contrasts with static text. In a scroll of
  dense text, the one moving thing draws the eye. Motion
  contrast, not motion volume.

## What does NOT transfer to us

- **Screen-share doc scroll is a developer-niche
  format.** Our audience is broader, and our bet is
  character. No character, no voice, no joke — nothing
  to send except utility. A doc scroll earns saves, not
  sends. Our engine needs sends.
- **Proof is weak.** The before/after demo is embedded
  but there is no split-screen comparison, no metrics,
  no code execution or results panel shown. A before
  clip without a visible after is a tease, not proof.
- **Naming flaws without showing fixes.** The checklist
  names generic flaws (flat timing, generic movement)
  but the reel does not show the fix for any of them.
  Our reels must show the fix — we show disasters AND
  fixes, with frames as evidence.
- **Unreadable at reel speed.** A dense doc scrolled
  fast cannot actually be read. Viewers get vibes, not
  content. If the artifact matters, it needs to be
  readable — or the reel is just an ad for the doc.

## What we apply

1. **Grading scale as a device.** A future reel grades
   OUR OWN reels on a visible scale — our real rubric
   scores (Motion 1→5, Captions, Audio) on screen.
   Self-grading as content, with real numbers, and the
   viewer places our work themselves.
2. **Flaw checklist as a diagnostic beat.** Name the
   exact flaw pattern in one line when Motto fails. We
   already do this in post-mortems; bring it on screen:
   one flaw, one frame, one fix.
3. **Our artifacts as content.** Our LOG and Mistake
   Ledger are real artifacts with real entries. A future
   reel can scroll the real Ledger as proof of learning
   — real entries, readable pace, Motto reacting to his
   own list. Same doc-as-content engine, our material.
4. **One moving element in a still frame.** When a beat
   is mostly static text or doc, keep one element
   animated — Motto blinking or bobbing in the corner —
   so the frame never fully dies.
